# Backend Homeworks

Монорепозиторий на NestJS из двух сервисов:

- `user-service`: REST API с регистрацией и JWT, профилем, аватарками в объектном
  хранилище, кошельком с переводами и фоновым обнулением балансов. После успешного
  перевода публикует событие в Kafka.
- `notification-service`: читает события о переводах из Kafka, сохраняет
  уведомления в MongoDB и отправляет их обоим участникам по WebSocket. Историю
  уведомлений отдаёт по HTTP запросу от клиента.

## Стек

- NestJS 12 (монорепозиторий Nest CLI), Node 24
- PostgreSQL + Sequelize, MongoDB + Mongoose, миграции обеих баз через umzug
- Kafka, Socket.IO
- Redis: кэш и очередь BullMQ
- MinIO (S3) для аватарок, sharp для обработки картинок
- Docker Compose
- Prometheus, Loki, Alloy и Grafana для метрик и логов
- Jest: юнит-тесты и e2e на testcontainers

## Запуск

Нужен Docker. Значения из `.env.example` рабочие для локального запуска:

```bash
cp .env.example .env
```

Всё в Docker одной командой - инфраструктура, миграции, оба сервиса, Prometheus,
Loki и Grafana:

```bash
docker compose --profile app --profile observability up -d --build
```

Для разработки инфраструктура поднимается в Docker, а сервисы запускаются локально
(нужна Node 24):

```bash
docker compose up -d
npm install
npm run migration:user:up
npm run migration:notification:up
npm run start:user:dev
npm run start:notification:dev   # во втором терминале
```

Без профилей compose поднимает только инфраструктуру. Сервисы в контейнерах
заняли бы порты 3000 и 3001, и локальный запуск с ними бы конфликтовал.

| Что                                     | Адрес                                                                             |
|-----------------------------------------|-----------------------------------------------------------------------------------|
| user-service API и Swagger              | `http://localhost:3000/api/v1`, `http://localhost:3000/api/v1/docs`               |
| notification-service: Socket.IO         | `ws://localhost:3001`                                                             |
| notification-service: история и Swagger | `http://localhost:3001/api/v1/notifications`, `http://localhost:3001/api/v1/docs` |
| Health и метрики обоих сервисов         | `/health/live`, `/health/ready`, `/metrics`                                       |
| Grafana, дашборд Backend homeworks      | `http://localhost:3030` (только с профилем `observability`)                       |
| Prometheus                              | `http://localhost:9090` (только с профилем `observability`)                       |
| Kafka UI                                | `http://localhost:8080`                                                           |
| Консоль MinIO                           | `http://localhost:9001`                                                           |

Подключиться к уведомлениям в Postman: новый запрос типа Socket.IO на
`ws://localhost:3001`, заголовок `Authorization: Bearer <accessToken>`, подписка
на событие `notification`. Access-токен выдаёт `POST /api/v1/auth/login`
в user-service.

## Миграции

Схемы обеих баз описаны миграциями umzug. Приложение структуру базы при старте
не меняет, миграции накатываются отдельной командой. У umzug нет блокировки
в базе: если бы каждая копия сервиса запускала миграции при старте, несколько
копий могли бы одновременно применять одну и ту же миграцию.

|                    | user-service (PostgreSQL)                           | notification-service (MongoDB)                              |
|--------------------|-----------------------------------------------------|-------------------------------------------------------------|
| Накатить           | `npm run migration:user:up`                         | `npm run migration:notification:up`                         |
| Откатить последнюю | `npm run migration:user:down`                       | `npm run migration:notification:down`                       |
| Что не применено   | `npm run migration:user:pending`                    | `npm run migration:notification:pending`                    |
| Создать новую      | `npm run migration:user:create -- add-something.ts` | `npm run migration:notification:create -- add-something.ts` |

Файлы лежат в `apps/<сервис>/src/databases/migrations`. В Docker миграции запускает
одноразовый контейнер из образа сервиса, и сервис стартует только после него.

В MongoDB миграции создают индексы. Mongoose умеет строить их сам при старте, но это
выключено, как `synchronize` в Postgres: построение индекса на большой коллекции
нагружает базу, и в продакшене так не делают. Зато notification-service при старте
сверяет индексы в базе со схемой и не запускается, если миграции не применены.
Без уникального индекса он молча сохранял бы дубли уведомлений.

## Что реализовано

Первая домашка: регистрация, логин, refresh с ротацией, logout, профиль
(`GET/PATCH/DELETE /users/me`), список пользователей с пагинацией и поиском,
мягкое удаление, Swagger.

Вторая домашка, все уровни:

- **линтер**: ESLint с typed linting, husky + lint-staged на pre-commit;
- **аватарки**: до 5 активных на пользователя, загрузка в MinIO, soft delete,
  только для своего профиля; `POST/DELETE /users/me/avatars`;
- **активные пользователи**: `GET /users/active` отдаёт пользователей с 2+
  активными аватарками, непустым описанием и возрастом в диапазоне, у каждого
  последняя загруженная аватарка;
- **кэш**: список и профиль пользователя кэшируются в Redis на 30 секунд;
- **кошелёк**: поле баланса, пополнение и перевод между пользователями
  в транзакции, идемпотентность по ключу; `GET /wallet/balance`,
  `POST /wallet/deposits`, `POST /wallet/transfers`;
- **обнуление балансов**: `POST /balance-resets` кладёт джобу в BullMQ,
  плюс расписание каждые 10 минут;
- **логирование**: pino на всех уровнях, от HTTP-запросов до джоб.

Третья домашка, все уровни:

- **монорепозиторий**: проект второй домашки стал `apps/user-service`, рядом
  появился `apps/notification-service`. Общий код вынесен в библиотеки:
  `libs/common` (фильтр ошибок, настройка HTTP и Swagger, проверка токена,
  health и метрики), `libs/contracts` (контракт события о переводе и JWT),
  `libs/testing` (помощники для e2e);
- **WebSocket**: gateway на Socket.IO, на событие `ping` сервер отвечает `pong`;
- **JWT и комнаты**: токен проверяется при подключении, с невалидным токеном
  соединение не устанавливается. Каждый сокет попадает в комнату своего
  пользователя `user:<id>`, поэтому уведомление приходит на все его устройства.
  Когда токен истекает, сервер отключает сокет;
- **Kafka**: после перевода user-service публикует событие
  `wallet.transfer.completed`, а notification-service отправляет уведомление
  отправителю и получателю. Событие записывается в таблицу outbox в одной
  транзакции с переводом, поэтому перевод не может пройти без события.
  Сообщения, которые не удалось обработать, уходят в топик
  `wallet.transfer.completed.dlq`;
- **MongoDB**: каждое уведомление сохраняется в историю, история отдаётся через
  `GET /api/v1/notifications` с курсорной пагинацией;
- **health и остановка**: `/health/live` и `/health/ready` в обоих сервисах.
  При остановке сервис сначала перестаёт получать новый трафик, потом закрывает
  соединения по порядку;
- **метрики**: `/metrics` в обоих сервисах, стандартные метрики Node.js, число
  WebSocket-подключений и отправленных уведомлений, состояние outbox.

Сверх задания: Docker-образы обоих сервисов и запуск всего проекта одной
командой, Grafana с дашбордом метрик и логами, e2e-тесты notification-service.

### Монорепа и библиотеки

Проект второй домашки переехал в `apps/user-service` командой `nest generate app`,
рядом появился `apps/notification-service`. Зависимости и настройки ESLint, Prettier
и Jest общие на весь репозиторий, у каждого приложения только свой
`tsconfig.app.json`. Импорты внутри приложения идут через алиас с его именем
(`@user-service/...`), библиотеки подключаются как `@libs/...`.

Сборка идёт через tsc. По умолчанию Nest в монорепе склеивает приложение в один
файл, и туда попадает только то, что импортирует `main.ts`. Мигратор, миграции
и скрипт очистки ключей идемпотентности запускаются отдельно от сервера, а мигратор
ещё и ищет файлы миграций по маске во время работы, поэтому в один файл они бы
не попали. SWC тоже не подошёл: в монорепе он не кладёт в сборку код из `libs/`.
Команды `nest generate app` и `nest generate library` дописывают в `nest-cli.json`
строку `"webpack": true`, которая перебивает tsc, поэтому после генерации её нужно
удалить.

Из-за tsc путь к собранному сервису длинный:
`dist/apps/user-service/apps/user-service/src/main.js`. Первая половина пути
это папка сборки приложения. У каждого приложения она своя, поэтому сборка одного
не стирает сборку другого. Вторая половина повторяет путь исходника от корня
репозитория: приложение импортирует код из `libs/`, и tsc сохраняет структуру
от их общей папки.

Код переезжает в библиотеку, только когда он нужен обоим сервисам. Пока им
пользуется один сервис, он живёт внутри него.

- `libs/common`: общая настройка HTTP (префикс, версия API, валидация, фильтр
  ошибок, Swagger), проверка access-токена для HTTP и WebSocket, health-проверка
  Kafka, метрики и настройки логгера.
- `libs/contracts`: топик и формат события о переводе, заголовки Kafka, payload
  JWT. Это договорённость между сервисами, поэтому она отделена от общего кода:
  правка здесь меняет то, что один сервис ждёт от другого, и это должно быть
  видно в диффе.
- `libs/testing`: помощники для e2e обоих сервисов (Kafka в контейнере,
  генерация ключей RSA, ожидание условий). Его импортируют только тесты, в сборку
  сервисов он не попадает.

### WebSocket

Уведомления отдаёт gateway на Socket.IO, он работает на том же порту, что и HTTP
notification-service. События типизированы: сервер шлёт `notification`, а на `ping`
отвечает `pong`.

Токен проверяется до подключения, в middleware Socket.IO. Основной способ передать
токен это поле `auth.token`, потому что браузерный WebSocket API не умеет задавать
заголовки. Заголовок `Authorization: Bearer` оставлен для инструментов вроде Postman.
Проверка общая с HTTP (`AccessTokenVerifier` в `libs/common`): подпись RS256
проверяется публичным ключом, а алгоритм зафиксирован, поэтому токен с подменённым
`alg` в заголовке не пройдёт. При отказе клиент получает код: `TOKEN_EXPIRED`
значит обновить токен через `/auth/refresh` и подключиться заново, `TOKEN_INVALID`
значит, что переподключаться бессмысленно.

Каждый сокет попадает в комнату своего пользователя `user:<id>`, и уведомление
отправляется в комнату. Так его получают все устройства пользователя сразу. Префикс
`user:` нужен, чтобы эти комнаты не пересекались с комнатами, которые Socket.IO
сам создаёт для каждого сокета по его id.

Токен проверяется только при подключении, а соединение может жить часами. Поэтому
сервер ставит таймер на момент истечения токена и отключает сокет. Без этого сокет
с давно истёкшим токеном продолжал бы получать уведомления.

Уведомление по сокету может потеряться: пользователь, который был офлайн, его
не получит. Поэтому надёжный источник уведомлений это история в MongoDB, и после
подключения клиент забирает пропущенное через `GET /api/v1/notifications`.
Уведомление может прийти и дважды, если Kafka доставит событие повторно. Id у него
тот же, и клиент отбрасывает дубль по id.

### Kafka и transactional outbox

#### На подумать: как не дать переводу и событию разойтись

Если отправлять событие после коммита перевода, оно потеряется, когда Kafka
недоступна или процесс упал между коммитом и отправкой. Если отправлять до коммита,
а транзакция откатится, придёт уведомление о переводе, которого не было. Одной
транзакцией базу и Kafka не связать.

Поэтому событие пишется в таблицу `outbox_events` в той же транзакции, что
и перевод: либо сохраняются оба, либо ничего. В Kafka события отправляет отдельный
цикл внутри сервиса (relay): читает таблицу, публикует и удаляет отправленное.
Пока Kafka лежит, события ждут в таблице, а переводы работают. После коммита
перевода relay получает сигнал и отправляет событие сразу, не дожидаясь следующего
опроса таблицы.

Relay рассчитан на несколько копий сервиса. Он забирает пачку событий через
`FOR UPDATE SKIP LOCKED` и ставит на неё аренду на 30 секунд. Две копии не возьмут
одно событие, а если копия упадёт посреди отправки, аренда истечёт и событие
заберёт другая.

Отказы при отправке relay делит на два вида. Если брокер ответил ошибкой, Kafka
работает, а проблема в самом событии, например нет топика. Такое событие
откладывается с растущей паузой от секунды до пяти минут, остальные уходят дальше,
и одно плохое событие не блокирует очередь. После 20 отказов (около часа) событие
откладывается насовсем: его разбирает человек, а метрика `outbox_failed_events`
становится больше нуля. Если брокер не ответил вовсе, значит лежит сама Kafka.
Тогда relay прерывает пачку, не засчитывает попытку событиям и повторяет через
паузу до 30 секунд.

В Kafka событие доходит хотя бы один раз: если relay упадёт после отправки, но до
удаления строки, событие уйдёт повторно. Поэтому notification-service обрабатывает
повтор без последствий (см. MongoDB). Ключ сообщения это id перевода, а в заголовке
`x-request-id` едет id HTTP-запроса: по нему перевод находится в логах обоих
сервисов.

На стороне notification-service невалидное событие сразу уходит в топик
`wallet.transfer.completed.dlq`. Иначе Nest считал бы ошибку временной, Kafka
доставляла бы событие снова и снова, и чтение партиции встало бы. Другие ошибки
обработки уходят туда же, кроме недоступной MongoDB: тогда сервис ждёт базу.

Топики создаёт контейнер `kafka-init`, автосоздание в Kafka выключено. Иначе
опечатка в имени топика создала бы новый пустой топик, и события молча уходили бы
в него. Транспорт Kafka в Nest работает на kafkajs, который не обновлялся с 2023
года. С Kafka 4.3 он работает, но это риск на будущее.

### MongoDB: история уведомлений

Один перевод даёт два документа: у отправителя `transfer.sent`, у получателя
`transfer.received`. Так лента пользователя читается одним проходом по индексу
`(userId, createdAt, _id)`, без фильтра «или я отправитель, или я получатель».
Общие поля лежат в корне документа, а поля конкретного типа уведомления в `data`:
у будущих типов, например пополнений, набор будет свой. Сумма хранится в
`Decimal128`, точном типе, как `numeric` в Postgres, а наружу отдаётся строкой.

Повторная доставка события из Kafka безопасна благодаря уникальному индексу
`(userId, eventId)`. Повторная вставка падает на нём, сервис считает это успехом
и отправляет уведомление по сокету ещё раз с тем же id: он не знает, дошло ли
уведомление в прошлый раз. Отдельная таблица обработанных событий не нужна,
идемпотентность обеспечивает сам индекс.

Если MongoDB недоступна, сообщение не уходит в DLQ: база вернётся, и событие нужно
просто обработать позже. Обработчик повторяет попытку раз в 5 секунд и всё это
время раз в 3 секунды отправляет Kafka heartbeat, иначе Kafka решила бы, что
consumer умер, и отдала бы партиции другому. При остановке сервиса ожидание
прерывается, и после перезапуска Kafka доставит событие снова. Пауза партиции из
документации kafkajs не подошла: при проверке consumer после нескольких ошибок
перезапускался, таймер возобновления срабатывал посреди перезапуска, и процесс
падал. Пока база лежит, чтение стоит целиком, и это осознанно: обрабатывать
события всё равно некуда.

Запись подтверждается только после того, как MongoDB сохранила её в журнал
на диске (`w: "majority", journal: true`). Сразу после записи сервис отправляет
уведомление, а Kafka запоминает, что событие обработано. Потерянную при падении
базы запись уже никто не повторил бы.

История отдаётся через `GET /api/v1/notifications`, id пользователя берётся только
из токена. Пагинация курсорная: пока пользователь листает ленту, сверху появляются
новые уведомления, и при offset на следующей странице повторялись бы уже
показанные. Сортировка идёт по времени сохранения уведомления в базу.
События одного пользователя приходят из разных партиций, и событие о более раннем
переводе может сохраниться позже. При сортировке по времени перевода оно попало бы
в середину уже просмотренных страниц, и клиент бы его не увидел.

Историей переводов эта лента не служит: данные о деньгах хранит Postgres, а в ленте
нет, например, пополнений. MongoDB работает без replica set: транзакции и потоки
изменений пока не нужны.

### Health-проверки и остановка

`/health/live` внешние зависимости не проверяет и просто отвечает, что процесс жив.
Единственное исключение в notification-service: liveness отвечает 503, если
consumer Kafka остановился насовсем. kafkajs сам перезапускает consumer после
временных ошибок, но после неисправимой события перестают читаться, и поможет только
перезапуск. Liveness сделан без terminus: при остановке terminus отвечает 503 на все
свои проверки, и оркестратор убил бы под посреди корректного завершения.

`/health/ready` проверяет базу сервиса (PostgreSQL или MongoDB) и Kafka. На каждую
проверку базы есть 1 секунда, иначе зависшая база задержала бы ответ дольше
таймаута пробы. Kafka проверяется в фоне раз в 10 секунд одним постоянным
клиентом, а readiness только читает последний результат. Встроенная проверка
terminus создаёт новое подключение к Kafka на каждый запрос пробы. Почему
недоступная Kafka даёт `degraded` вместо 503, описано в отступлениях от задания.

Health и метрики живут вне префикса `/api/v1`, не пишутся в логи и не попадают под
rate limit. Проба раз в 5 секунд уже превысила бы лимит в 10 запросов в минуту,
получила бы 429, и оркестратор посчитал бы сервис мёртвым.

#### На подумать: почему liveness не проверяет базу

Liveness отвечает на вопрос «поможет ли перезапуск этого процесса?». Если упала база,
перезапуск не поможет: Kubernetes перезапустил бы все поды разом, оборвал бы
запросы и WebSocket-соединения и добавил бы нагрузки базе, которая и так
поднимается. Документация Kubernetes прямо предупреждает, что такие проверки
приводят к каскадным отказам. Недоступную зависимость проверяет readiness: под
перестаёт получать трафик, но продолжает работать и сам вернётся в балансировку,
когда зависимость поднимется.

#### Остановка

`enableShutdownHooks` включён с `useProcessExit: true`. Без этой опции Nest
завершает процесс сигналом, и pino не успевает дописать логи остановки.

Порядок остановки по сигналу SIGTERM:

1. Останавливаются фоновые задачи: relay outbox, проверка Kafka, ожидание MongoDB.
2. Readiness начинает отвечать 503, и 5 секунд сервис продолжает принимать
   запросы. Балансировщик узнаёт об остановке пода не мгновенно, и запросы
   в это время не должны падать.
3. Закрываются Socket.IO, HTTP-сервер (он дожидается запросов, которые уже
   выполняются) и consumer Kafka (он дожидается текущего сообщения).
4. Закрываются соединения с PostgreSQL, MongoDB, Redis и producer Kafka.

Каждый этап пишется в лог, остановку видно по логам при `docker compose stop`.
На Ctrl+C (SIGINT) пауза из второго шага не делается. Если Kafka зависла, relay
может держать первый шаг до 10 секунд, и readiness всё это время отвечает 200.
В Kubernetes это неважно: под убирают из балансировки в момент удаления,
не дожидаясь пробы.

### Метрики

Оба сервиса отдают метрики на `/metrics` в текстовом формате Prometheus. Кроме
стандартных метрик Node.js (CPU, память, heap, задержка и загрузка event loop,
сборка мусора, дескрипторы), есть свои:

| Метрика | Тип | Что показывает |
|---|---|---|
| `http_request_duration_seconds` | Histogram | Время ответа HTTP по методу, маршруту и статусу |
| `notification_websocket_connections` | Gauge | Открытые WebSocket-подключения |
| `notification_sent_total` | Counter | Отправленные уведомления по типу |
| `notification_dead_letters_total` | Counter | Сообщения, ушедшие в DLQ, по причине |
| `kafka_available` | Gauge | Ответила ли Kafka на последнюю фоновую проверку |
| `outbox_events_published_total`, `outbox_publish_errors_total` | Counter | Отправки relay и неудачные попытки |
| `outbox_pending_events`, `outbox_oldest_pending_event_age_seconds`, `outbox_failed_events` | Gauge | Очередь outbox: сколько ждёт, сколько ждёт самое старое событие, сколько отложено насовсем |

В метках нет id пользователя и реального URL. Каждое сочетание меток Prometheus
хранит как отдельный ряд, и id пользователя в метке дал бы по ряду на каждого
пользователя. Поэтому в `route` пишется шаблон маршрута (`/users/:id`), а не
`/users/42`.

Метрики очереди outbox считаются SQL-запросом в момент опроса `/metrics`, поэтому
Prometheus видит состояние базы ровно на момент опроса. На запрос даётся
1 секунда, и одновременно идёт только один. Если запрос упал, метрики сохраняют
прошлые значения, а `outbox_stats_up` становится 0. Ошибка внутри одной метрики
иначе уронила бы весь ответ `/metrics`.

#### На подумать: Gauge или Counter

Gauge показывает текущее значение, которое растёт и падает. Число подключений
как раз такое: подключился клиент, значение выросло, отключился, упало.
Counter только растёт и обнуляется при перезапуске процесса. По нему смотрят
скорость (`rate`) или прирост за период (`increase`), и эти функции Prometheus
сами учитывают обнуление. Число отправленных уведомлений только копится, поэтому
для него Counter: `notification_sent_total`.

### Docker

Один Dockerfile собирает два образа. Сборка у сервисов общая (один `package.json`
и общий код в `libs/`), отличаются только последние шаги, поэтому в файле две
финальные стадии с именами сервисов. Нужная выбирается флагом `--target`:

```bash
docker build --target user-service -t backend-homeworks/user-service .
```

Зависимости ставятся дважды. Для сборки нужны TypeScript и Nest CLI, а в образ
идут только зависимости для работы, поэтому компилятора, тестов и исходников в
образе нет. Слой с `node_modules` у двух образов общий и хранится один раз. Минус
монорепы с одним `package.json`: в образ user-service попадают и пакеты
notification-service, например mongoose.

Базовый образ `node:24.22.0-alpine3.24` с точной версией, чтобы повторная сборка
давала тот же образ. Alpine выбран ради размера: при скачивании это 62 МБ против
83 МБ у Debian slim.
Но на Alpine вместо привычной glibc библиотека musl, сборка Node под неё
считается экспериментальной, и не у всех нативных пакетов есть готовые бинарники
под musl. Если с этим начнутся проблемы, переход на slim займёт одну строку.

Зависимости ставятся с `--ignore-scripts`. Скрипт `prepare` запускает husky, а
в продакшен-зависимостях его нет, и установка упала бы. argon2 и sharp скрипты
не нужны, они грузят готовые бинарники при первом `require`. Чтобы проблема
с бинарником под musl всплыла ещё при сборке образа, в Dockerfile стоит проверка
`node -e "require('argon2'); require('sharp')"`.

Процесс работает от пользователя `node` и запускается напрямую через `node`, без
`npm`: npm встаёт между Docker и приложением, и сигнал остановки доходит до Node
ненадёжно. Миграции запускаются из того же образа другой командой, в compose это
одноразовый контейнер, после которого стартует сервис.

В контейнеры попадают два env-файла: `.env` и `.env.docker`. Внутри сети compose
у зависимостей другие адреса, чем на хосте (`postgres:5432` вместо
`localhost:5433`), и `.env.docker` перекрывает только их и режим запуска:
`NODE_ENV=production`, логи в JSON без pino-pretty, уровень `info`. Docker по
умолчанию ждёт остановки 10 секунд, а остановка сервиса с паузой для балансировщика
может занять до 20 секунд, поэтому в compose стоит `stop_grace_period: 30s`.

### Наблюдаемость

Профиль `observability` поднимает четыре контейнера:

- Prometheus раз в 15 секунд забирает `/metrics` у обоих сервисов и хранит
  метрики 7 дней;
- Alloy читает логи контейнеров сервисов через Docker API и отправляет их в Loki;
- Loki хранит логи;
- Grafana показывает и то, и другое.

Для сбора логов взят Alloy: прежний агент Grafana, Promtail, перестали
поддерживать в марте 2026 года, и Alloy его замена. Сервисы пишут логи в JSON,
Alloy достаёт из каждой строки уровень и вместе с именем сервиса делает его меткой.
Остальные поля остаются внутри строки и разбираются в момент запроса. Loki ищет
по меткам и хранит каждое их сочетание отдельным потоком, поэтому метками стали
только сервис и уровень: у них мало разных значений. `requestId` или id
пользователя в метке дали бы тысячи потоков.

Источники данных и дашборд Grafana подключает из файлов в `docker/grafana` при
старте, руками ничего настраивать не нужно. На дашборде «Backend homeworks»
разделы HTTP, уведомления, outbox, состояние сервисов, Node.js и логи, сверху
фильтры по сервису и уровню логов. Раздел Node.js собран по шаблону Grafana Labs
(дашборд 14058 на grafana.com): оттуда взят набор панелей и запросы. Добавлены
загрузка event loop и файловые дескрипторы, которых в шаблоне нет. В логах видны
контекст и сообщение, у запросов ещё метод, путь, статус и время ответа.

Дашборд хранится в репозитории, и сохранять его из интерфейса Grafana запрещено.
Иначе правка осталась бы только в базе Grafana и не попала бы в git. Чтобы
поменять дашборд, его правят в интерфейсе, выгружают JSON через Export и заменяют
файл. Grafana перечитывает его сама за несколько секунд.

Grafana открывается без пароля с правами админа, поэтому её порт опубликован
только на `127.0.0.1`. Alloy видит Docker целиком через `docker.sock`. Для
локального стенда это допустимо, в продакшене логи собирают агентом на каждом
узле без доступа к Docker API. Метрики и логи собираются только у сервисов
в контейнерах: при запуске через `npm run start:*:dev` логи остаются в терминале.

## Технические моменты второй домашки

### Линтер

ESLint в режиме с типами (`recommendedTypeChecked`) включён ради правил, которые ловят
баги, а не стиль: `no-floating-promises` находит промисы, которые забыли
дождаться, а запрет циклических импортов находит циклы, которые в Nest всплывают только
в рантайме как `undefined` вместо зависимости. Порог предупреждений равен нулю:
предупреждение, которое можно игнорировать, будут игнорировать. На pre-commit
lint-staged проверяет только изменённые файлы.

### Auth и пользователи

**Транзакции.** Регистрация создаёт пользователя и сразу выдаёт ему refresh-токен.
Оба шага идут в одной транзакции, чтобы при сбое не остался пользователь без сессии (или
наоборот). Refresh тоже транзакционный: старый токен удаляется и выдаётся новый
атомарно, иначе можно было бы либо потерять сессию, либо получить два валидных токена
одновременно. По той же логике удаление аккаунта (soft-delete + отзыв всех
refresh-сессий) идёт одной транзакцией.

**Уникальность при мягком удалении.** Удаление мягкое (`paranoid`), поэтому обычный
unique-констрейнт на login/email не дал бы заново занять логин удалённого пользователя.
Вместо этого уникальность держится на частичных индексах `where deletedAt is null`
(см. `user.model.ts`). Они действуют только среди живых строк, так что новые
пользователи с удалёнными не конфликтуют. Paranoid при этом сам добавляет
`deletedAt is null` в выборки, и удалённые записи не всплывают ни в проверках,
ни в поиске.

**Токены.** Access-токен короткоживущий, это JWT с минимальным payload (только `sub`). Refresh
лежит в httpOnly cookie с ограниченным path, а в БД хранится только его sha256-хэш:
даже при утечке дампа по нему нельзя восстановить валидный токен.

### Аватарки

Multer режет файлы больше 10 МБ ещё на приёме. Pipe проверяет тип не по
`Content-Type` (его ставит клиент), а по первым байтам файла.

Проверка сигнатуры смотрит только первые байты, а внутрь валидной картинки
можно дописать что угодно, от скрипта до архива. При этом файл из бакета
публично раздаётся другим пользователям. Поэтому в хранилище никогда не
попадает присланный файл: sharp декодирует его в пиксели и собирает новый
webp размером 512×512. В новом файле есть только пиксели: EXIF с GPS-координатами
съёмки, цветовые профили и дописанный мусор до хранилища не доезжают.
Если файл не декодируется, сервис отвечает 422.

Webp выбран потому, что при том же визуальном качестве он весит заметно меньше jpeg
и png и поддерживается всеми современными браузерами; заодно на выходе всегда
один формат, независимо от того, что прислали. Размер 512×512 выбран потому, что аватарка
в интерфейсе показывается маленькой: 512 покрывает вдвое больший размер
отображения с запасом под retina-экраны, а хранить больше значит платить за байты,
которые никто не увидит.

От декомпрешн-бомбы (PNG в пару килобайт, разворачивающийся в гигабайты
пикселей) проверка веса не спасает. Спасает потолок в 50 мегапикселей: sharp
читает размеры из заголовка и отклоняет картинку до выделения памяти.

Файл заливается в MinIO до транзакции БД, чтобы не держать её открытой на время
сетевого вызова. Если вставка в БД упала, в бакете остаётся невидимый файл-сирота,
и сервис удаляет его сам в обработке ошибки.

Лимит в 5 активных аватарок проверяется в транзакции под `FOR UPDATE` на строке
пользователя: без лока два параллельных запроса насчитали бы по четыре и вставили
шестую. Проверка есть и до обработки: она даёт быстрый отказ без работы sharp и MinIO.

Удаление мягкое (soft delete), слот освобождается. Принадлежность зашита в запрос
(`WHERE id = ? AND userId = ?`); на чужую аватарку сервис отвечает 404, ведь 403 подтвердил бы,
что такой id существует.

### Активные пользователи

Запрос написан на SQL, а не через ORM. На SQL это два подзапроса
`JOIN LATERAL`: один считает активные аватарки, второй достаёт последнюю.
`LATERAL` здесь потому, что подзапрос видит текущую строку пользователя:
«последняя аватарка» превращается в точечный заход в индекс по
`ORDER BY "createdAt" DESC LIMIT 1`, а не в проход по всем аватаркам
с оконной функцией. Оба подзапроса работают по частичному индексу,
в котором нет удалённых аватарок.

Для страниц используется курсорная пагинация (keyset), а не offset. Offset на
глубине работает всё дороже: для сотой страницы постгресу пришлось бы прочитать
девяносто девять предыдущих и выбросить их. Курсор хранит `(age, id)` последней
отданной строки, и следующая страница читается по индексу сразу с нужного
места. Цена кейсета в том, что нельзя прыгнуть на произвольную страницу, листать
можно только последовательно; для ленты «самых активных» это нормально, номер
страницы здесь никому не нужен. Отсюда же `id` в паре: сортировка курсора
обязана быть уникальной, иначе пользователи с одинаковым возрастом терялись бы
на границе страниц. Под условия запроса построен свой частичный индекс
`(age, id)` по неудалённым пользователям с непустым описанием.

Худший случай для этого запроса: широкий диапазон возраста, в котором почти
ни у кого нет двух аватарок. Постгрес перебирает пользователей одного за
другим, почти никого не находит и может работать так очень долго. Поэтому
на транзакции стоит `statement_timeout`: затянувшийся запрос обрывается,
клиент получает ошибку, а соединение с базой освобождается.

### Кэш

Список пользователей и профиль кэшируются в Redis на 30 секунд. В кэш кладётся
не модель из БД, а response DTO, поэтому хэш пароля не попадает в Redis и не
может утечь вместе с дампом кэша.

Профиль инвалидируется просто: при обновлении или удалении пользователя его
ключ стирается. Со списком так не получится: он кэшируется по комбинации
страницы, лимита и поискового запроса, и таких ключей много. Вместо перебора
ключей в ключ списка входит версия: любое изменение состава пользователей
(регистрация, обновление, удаление) записывает новую версию, после чего старые
ключи становятся недостижимыми и умирают по TTL сами. Версией служит временная
метка: текущее время всегда больше предыдущего, поэтому не нужно атомарно
инкрементить счётчик, а если Redis потеряет ключ версии (рестарт, TTL), новая
метка всё равно не совпадёт ни с одной старой, а счётчик начал бы с нуля и
мог воскресить устаревшие кэши. При регистрации версия сбрасывается только после
коммита транзакции: если сбросить раньше, параллельный запрос успел бы
закэшировать список ещё без нового пользователя, но уже под новой версией.

Ошибка Redis не роняет запрос: запись и удаление ключей обёрнуты, сбой
логируется, а данные читаются из БД.

Баланса в кэшируемом профиле нет. Он меняется в обход профиля (переводами,
пополнениями, фоновым обнулением), и ни одна из этих операций кэш профиля не
сбрасывает. Попади баланс в DTO, пользователь сразу после перевода видел бы
старую сумму ещё до 30 секунд, а устаревший баланс выглядит как пропавшие
деньги. Поэтому баланс отдаёт отдельная ручка, которая всегда ходит в БД,
а `Cache-Control: no-store` запрещает кэшировать ответ ещё и клиенту с прокси.

### Кошелёк

Деньги хранятся как `DECIMAL(19,2)`: это точный тип, без ошибок округления. В коде сумма
нигде не превращается в `number`: жёсткое правило одно: не считать деньги во float
(`0.1 + 0.2` в JS даёт не `0.3`). Соблюсти его можно двумя способами: decimal-библиотека
в коде или счёт в базе. Выбрал базу: вся арифметика здесь сводится к простым списанию
и зачислению без комиссий и округлений, и их всё равно нужно делать атомарным `UPDATE`,
а Postgres складывает `DECIMAL` точно. Драйвер `pg` к тому же возвращает `DECIMAL`
строкой, так что `number` в этой схеме просто негде появиться. Появись комиссии или
конвертация, переехал бы на decimal-библиотеку: считал бы в коде, а в SQL отдавал
готовую дельту, чтобы правила округления были покрыты тестами.

По HTTP суммы тоже ходят строками (`"1000.00"`). Передачу число бы пережило, но клиент
рано или поздно начнёт считать, и `parseFloat` вернёт ту самую float-ошибку, от которой
я защищался в базе. Строка к тому же превращает тихую ошибку в громкую:
`"20.51" + "10.00"` даст мусор, который заметят сразу, а `20.51 + 10.00` даст
правдоподобное число, которое иногда неверно. Формат подсмотрел у криптовалютных API:
у эфириума точность выше, чем держит double, поэтому суммы там ходят только
строками с фиксированной точностью. Отсюда и жёсткое ограничение на `amount`: до
12 цифр до точки и до двух после, проверяется регуляркой в DTO: `@IsNumber()` /
`@Min()` на строке не работают.

Списание делается одной атомарной операцией `UPDATE ... WHERE balance >= amount`: проверка
остатка и вычитание не разнесены во времени, поэтому два параллельных перевода
не уведут баланс в минус. На случай, если эту проверку сломают при рефакторинге,
в БД стоят CHECK-констрейнты (`balance >= 0` и верхняя граница): схема поймает баг
кода, и отрицательный баланс в таблицу всё равно не попадёт.

Перевод идёт в транзакции, и первым делом она блокирует строки обоих участников
`FOR UPDATE`, всегда по возрастанию id. Без фиксированного порядка встречные переводы
A→B и B→A взяли бы локи навстречу друг другу и попали в дедлок.

Сеть ненадёжна: клиент, не дождавшийся ответа, повторит запрос, и без защиты деньги
спишутся дважды. Поэтому оба денежных роута требуют заголовок `Idempotency-Key`.
Явной проверки «занят ли ключ» нет намеренно: она сама была бы гонкой: пока один
запрос проверил и выполнял, ключ занял бы параллельный. Вместо этого ключ пишется
в той же транзакции, что и операция, и вся защита держится на unique-констрейнте
`(userId, endpoint, key)`: повтор падает по уникальности, и сервис отдаёт результат
первой операции: тот же 201 плюс заголовок `Idempotency-Replayed: true`. Рядом
с ключом лежит хэш параметров запроса: тот же ключ с другой суммой или получателем
считается не повтором, а ошибкой клиента (409), иначе он получил бы в ответ чужую операцию
и решил, что прошла его.

Ошибки кошелька отдаются с машиночитаемым полем `code` (`INSUFFICIENT_FUNDS`,
`IDEMPOTENCY_KEY_REUSED`, …), и клиент различает их, не разбирая текст сообщения.

Каждая операция пишется в таблицу `transfers` с историей движения денег. Баланс сам по себе
агрегат, по нему не видно, откуда взялись деньги; строка перевода отвечает, кто, кому,
сколько и когда. Пополнение (`POST /wallet/deposits`) хранится там же и отличается
`NULL` в отправителе; сам роут добавлен, чтобы переводы можно было проверить руками
и тестами. В реальной системе деньги приходили бы от платёжного провайдера. У строки
ключа идемпотентности стоит внешний ключ на строку перевода: по нему при повторе
и находится уже выполненная операция.

В задании для транзакций указан `typeorm-transactional`, но проект с первой
домашки написан на Sequelize, и переезжать на другую ORM ради одной зависимости смысла
нет. Транзакции сделаны средствами Sequelize (`sequelize.transaction` с колбэком);
требования уровня (атомарность перевода и запрет отрицательного баланса) выполняются.

### Обнуление балансов

Роут `POST /balance-resets` кладёт джобу в очередь BullMQ и сразу отвечает 202
с идентификатором прогона. Само обнуление выполняет воркер: пользователей может быть
много, держать HTTP-запрос открытым всё это время нельзя. Расписание работает через
ту же очередь: каждые 10 минут планировщик BullMQ кладёт ту же джобу, что и роут.

Пока один прогон стоит в очереди или выполняется, второй не запускается: джоба
добавляется с ключом дедупликации, и повторный запрос получает в ответ уже существующий
прогон с пометкой `deduplicated`. У ключа есть TTL: если процесс убьют и снять ключ
будет некому, он истечёт сам, и очередь не останется заблокированной навсегда.

Воркер обнуляет балансы пачками, каждая пачка идёт отдельной короткой транзакцией: выбрать
очередных пользователей с ненулевым балансом под `FOR UPDATE`, обнулить и в той же
транзакции записать списания в аудит. Выполняется либо и то и другое, либо ничего. Одна транзакция
на всю таблицу держала бы блокировки на всех пользователях до конца прогона, и всё это
время не прошёл бы ни один перевод. Строки берутся по возрастанию id, в том же порядке,
в котором лочит участников перевод, поэтому встречный дедлок с кошельком невозможен.
Между пачками воркер двигается курсором по id и никого не обрабатывает дважды.

Упавший прогон BullMQ повторяет, до трёх попыток с растущей паузой. Повтор безопасен:
в выборку попадают только пользователи с балансом больше нуля, поэтому те, кого успела
обнулить прошлая попытка, второй раз не трогаются и в аудите не задваиваются.

Обнуление балансов массовое и необратимое, поэтому оно журналируется в двух таблицах.
`balance_reset_runs` хранит попытки прогонов: статус, число обработанных пользователей,
сумму списанного, текст ошибки при падении. `balance_resets` хранит списания построчно:
какой баланс был у пользователя до обнуления и в какой попытке его списали.

### Логирование

Логгер: pino (nestjs-pino). Выбран потому, что логи в проде читает не человек,
а сборщик вроде Loki или Kibana, поэтому запись делается не строкой, а JSON с полями:
по строке можно только грепать текст, а по полям можно делать запросы («все операции
пользователя за час», «все запросы дольше 500мс»). Штатный нестовский `ConsoleLogger`
JSON выводить умеет, но это весь его функционал: ни redact, ни сквозного request-id,
ни HTTP-логов, всю обвязку пришлось бы писать самому. Pino при этом почти ничего
не стоит в горячем пути: приложение только сериализует JSON в stdout, а форматирование
и доставку логов делает внешняя инфраструктура; если же транспорт нужен внутри процесса
(как pino-pretty в dev-режиме), pino выносит его в отдельный worker thread.

Каждый уровень используется по назначению: debug для деталей вроде кэш-хитов, info
для бизнес-событий, warn для ожидаемых отказов, error для нарушенных инвариантов.
У каждого запроса есть сквозной id: он берётся из заголовка `X-Request-Id`, если
пришёл от прокси, иначе генерируется и возвращается клиенту. По нему все записи
одного запроса находятся одним поиском. Чувствительные поля (токены, пароли, куки)
вырезаются на уровне логгера (`redact`), а не по памяти в каждом сервисе: даже если
кто-то залогирует объект с паролем, в вывод он не попадёт.

## Тесты

```bash
npm test                       # юнит-тесты обоих сервисов и библиотек
npm run test:cov               # юнит-тесты с покрытием
npm run test:e2e               # e2e обоих сервисов, нужен запущенный Docker
npm run test:e2e:user          # e2e только user-service
npm run test:e2e:notification  # e2e только notification-service
```

Юнит-тестами покрыта бизнес-логика, то есть сервисы с ветвлениями и решениями: auth
(логин, ротация refresh, протухший токен), пользователи (конфликты login/email,
пагинация, маппинг в DTO без пароля), аватарки (лимит, отказ до похода в хранилище,
удаление файла-сироты при падении вставки), кэш (версии списка, поведение при
недоступном Redis), обнуление балансов (курсор, пустые батчи, фиксация упавшего
прогона). В третьей домашке добавились тесты на relay outbox (отказы брокера,
отложенные события, недоступная Kafka), на фильтр DLQ (что уходит в DLQ, а что
нет), на ожидание MongoDB и на проверку access-токена: истёкший токен, чужой ключ,
подмена payload, `alg: none`, подпись другим алгоритмом.

Контракты роутов (коды ответов, заголовки, состояние БД и бакета после запроса)
закрывают e2e-тесты. Они поднимают в testcontainers настоящие Postgres, Redis и MinIO,
без моков инфраструктуры: приложение в тестах ходит в те же хранилища, что и при
обычном запуске. Спек аватарок, например, сверяет, что после отказа валидации в БД
и бакете ничего не появилось, а после успешной загрузки в бакете лежит пересобранный
файл, а не присланные байты.

Kafka и MongoDB в e2e тоже настоящие. Для Kafka взят образ
`confluentinc/cp-kafka:8.3.2`: модуль `@testcontainers/kafka` рассчитан на образы
Confluent, а версия 8.3 собрана на Kafka 4.3, той же, что в нашем `apache/kafka`.
MongoDB запускается обычным контейнером `mongo:8.0`, потому что официальный модуль
поднимает replica set, а у нас одиночный сервер. Что проверяется:

- user-service: перевод записывает событие в outbox, повтор с тем же ключом
  второго события не создаёт, отклонённый перевод не создаёт ни одного; relay
  доставляет событие в Kafka и удаляет его из outbox; при недоступной Kafka сервис
  остаётся ready со статусом `degraded`, перевод проходит, событие ждёт в outbox;
- notification-service: перевод приходит по сокету обоим участникам и сохраняется
  в их историю; повторное событие сохраняется один раз; невалидное событие уходит
  в DLQ, и партиция читается дальше; сокет отключается, когда истекает токен;
  история не отдаётся без токена, не показывает чужие уведомления и листается
  без пропусков и повторов.

Падение MongoDB посреди обработки в e2e не проверяется. После перезапуска контейнер
получает другой порт, а при паузе контейнера каждый тест ждал бы таймаута драйвера.
Этот сценарий покрыт юнит-тестом и проверен вручную.

Отдельный спек гоняет кошелёк в конкурентном режиме: десять параллельных переводов
с одного баланса, встречные переводы двух пользователей друг другу, пять одновременных
запросов с одним ключом идемпотентности. Один прогон может и не поймать гонку, поэтому
тест проверяет инвариант, обязанный выполняться при любом порядке запросов: сумма всех
балансов в системе равна сумме заведённых в неё денег, а операция с одним ключом
выполнилась ровно один раз.

Покрытие считается по всем файлам, включая тонкую обвязку (модули, контроллеры,
конфиги), поэтому общая цифра скромнее, чем на бизнес-логике. Обвязку юнит-тестами
намеренно не трогаю: её корректность ловят типы и сборка, а сценарии закрывают e2e.

## Что дальше

Часть проекта к нескольким копиям сервиса уже готова: relay outbox делит события
через аренду, BullMQ раздаёт задачи между копиями, Kafka делит партиции между
consumer'ами. Чтобы запускать несколько копий, например в Kubernetes, осталось:

- подключить Redis-адаптер Socket.IO. Комнаты живут в памяти процесса, и
  уведомление, которое обработала одна копия, не дошло бы до сокета, подключённого
  к другой;
- оставить у Socket.IO только транспорт `websocket`. По умолчанию клиент начинает
  с long-polling, а это несколько HTTP-запросов, которые должны попасть в одну копию;
- перенести счётчики rate limit в Redis, иначе у каждой копии свой лимит. Пакет,
  на который ссылается документация Nest, пока не поддерживает Nest 12;
- включить `trust proxy` с адресом балансировщика. Без этого все клиенты приходят
  с его IP и делят один лимит на всех;
- увеличить число партиций Kafka: события читают не больше копий
  notification-service, чем партиций в топике (сейчас 3).

Для Kubernetes ещё нужны:

- миграции отдельным Job перед выкаткой;
- startupProbe. Без MongoDB notification-service пытается подключиться около
  5 минут (9 попыток по 30 секунд и паузы между ними), всё это время HTTP-порт
  закрыт, и liveness-проба убила бы под раньше;
- `terminationGracePeriodSeconds` с запасом над временем остановки;
- отдельные секреты для сервисов: приватный ключ JWT нужен только user-service,
  а сейчас через общий `.env` его получают оба.

Из наблюдаемости не сделаны трейсы (OpenTelemetry и Tempo) и алерты: на возраст
очереди outbox, отложенные события, рост DLQ, долю ответов 5xx и время ответа.
